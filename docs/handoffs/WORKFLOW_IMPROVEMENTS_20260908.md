# 条款、证据与补写工作流改进

本轮承接医院项目验收发现的问题：招标要求混入评标机构流程，部分项目事实没有关联完整原文，模型失败提示和实际资料待办混在一起，已写好的内容缺少局部修复办法。

## 使用顺序

1. 在“招标解析”查看分类建议及原文页码。明确技术要求进入章节；资格、商务、合同进入各自清单。非技术建议需实际人员复核，不能由系统自动缩小正式验收范围。评分和否决条件仍保留。
2. 在“处理待办”分别处理范围、正文、证据和实际资料。三个数字分别代表已映射、已回应、已签审；系统生成过文字不等于已回应，更不等于已签审。
3. 已有正文能够回应条款时，使用“定位现有正文响应”，选择对应章节并摘录当前正文原句。绑定记录要求实际复核人、条款指纹和正文版本；随后仍需章节签审。
4. 生成失败或漏回应时，优先修复失败分段。有效分段、引用顺序及旧版本保留。人工编辑、资料变化、来源撤回或生成期间发生修改时，系统要求重新载入并采取相应处理。
5. 对工程事实先查看本项目原文页码及匹配原因。没有依据的数字、承诺和前提变化继续提示；专业人员补充依据或修改实际正文。核验人和依据必须手填，系统不会代签。
6. 资料或证据规则变化后运行“重新核验证据”，再进行章节与整本签审。交付页继续区分送审和正式版本。

## 已落实的约束

- 保留原条款 ID、原文、页码、已有正文和交付历史；批量分类、映射、响应及审计在同一事务内完成。
- 技术范围不因自动建议减少。已人工确认的资格、商务、合同条款若缺少响应或不适用依据，仍独立阻断交付。
- 工期、面积、项目身份及地点优先绑定完整本项目招标原文；相同数字出现在其他对象、其他标段或另一项目中不能作为证明。
- 复合句逐项核验；验收或审批前提、通知主体、否定条件、范围和单位不得丢失。较长句子和后续条目不会因原有长度限制被静默跳过。
- 机器失败、证据缺口与实际资料待办分开；签审不能通过填写一句“已处理”掩盖未完成正文。
- 招标原文或原文加少量装饰词不能冒充技术响应。普通正文编辑不会把历史回退响应自动升为有效回应。
- 局部修复检查上下文、正文版本、有效发布来源和分段摘要。取消或并发修改时不保存半成品；成功保存为新版本。
- 人工表述核验绑定姓名、依据、正文和项目来源版本；撤回或重新核验会使相关签审失效，历史事件保留。

## 验证范围与数据

主服务使用 `http://127.0.0.1:8876/`。所有医院项目验证在独立 PostgreSQL 数据库 `bid_writer_validation_20260908` 和 `http://127.0.0.1:8877/` 完成。主库在本轮迁移前已完成自定义格式备份、SHA-256 校验及目录可读取检查。

原医院验证项目保留 773 条要求、11 章目录及 10 章草稿。最终使用 `project-evidence-1.0.1` 完整原文重查，正文版本、正文 SHA-256、条款 ID 和原文页码全部不变，模型调用增加为 0。原有 88 项混合提示中，实际资料项为 38 项。修正了工期、北区面积、质量目标和腾退期限等 6 项原有误报；没有把“预留 20%”“零投诉”等无依据承诺直接放行。新核验同时覆盖了以前遗漏的长句和短数值句，因此不能只比较风险总数来宣称准确率提升。

最终工作台显示：434 条已映射、21 条有可核验正文回应、0 条已签审。原文摘抄和结构化回退文字不再被算作有效响应。773 条仍为待人工复核情况下的正式验收范围，没有通过自动分类缩小分母。671 项待办包含 462 项范围处理、86 项正文响应定位、78 项高风险证据、38 项实际资料、7 项生成处理；生成处理包含缺失章节，不表示已有 7 章模型失败。
